# Use the AI SDLC Loop in your coding harness

This page takes you from nothing to your first loop in a new project. It covers the coding harnesses the project script supports. A harness is the coding agent you work in, such as Cursor or Claude Code. Pick yours in [Harness by harness](#harness-by-harness) when the steps below send you there. On your own, or new to code, and using Cursor? Skip to [Bootstrap for Cursor](#bootstrap-for-cursor).

The project is alpha. The agents and commands work, but they have not been tested in every harness on real projects yet. Tell us what breaks: [open an issue](https://github.com/mitulamin/ai-sdlc-loop/issues).

## What you need

- git and bash. On Windows, use WSL or Git Bash.
- Python 3, for any harness other than `none`. The installer uses the standard library only.
- Your harness, installed and signed in. Each harness section below links to its install guide.

## 1. Clone this repo

```bash
git clone https://github.com/mitulamin/ai-sdlc-loop
cd ai-sdlc-loop
```

You run the script from this clone. Your new project is a separate folder and a separate git repository.

## 2. Create your project

Give the script a target folder, an optional profile, and your harness:

```bash
scripts/new-project.sh --harness claude-code ../my-app              # solo, the default profile
scripts/new-project.sh --harness cursor ../my-app small-team
scripts/new-project.sh ../my-app large-org --harness=copilot-vscode  # options can go anywhere
scripts/new-project.sh ../my-app                                     # no harness: the template only
scripts/new-project.sh --help                                        # every profile and harness
```

`--help` lists the profile names and the harness IDs. The IDs are also in the table in the next step. A profile sets how much ceremony you get: gates, roles, review and ownership. See [Pick a profile](../README.md#pick-a-profile) in the README. If you are unsure, start with the default and add ceremony later.

The script copies the shared base from `template/`, applies the profile, installs the harness files, and runs `git init`. It refuses a target folder that is not empty, and it checks the harness name before it creates anything.

Everything is written inside the new project. The script never writes to your home folder or to a harness's user or global settings, so it cannot change your other projects. Delete the folder and nothing is left behind.

## 3. What gets installed where

From the template you get the always-on rules file `AGENTS.md`, the process for your profile in `PROCESS.md`, a `README.md`, a `CHANGELOG.md`, an MIT `LICENSE`, and the profile's extra files.

With a harness you also get this repo's skills, agents and loop commands, written to the folders that harness reads from its project, with the front matter and file names it expects:

- **Skills**: one folder per skill, each with its `SKILL.md` and the `SOURCES.md` that credits where it came from.
- **Agents**: the coordinator, and a producer and an adversarial reviewer for each phase.
- **Loop commands**: one per loop step, named with the `sdlc-` prefix.

The layout for each harness is data, in [data/harnesses.json](../data/harnesses.json), and `scripts/install-harness.py` builds the files from `skills/`, `agents/` and `commands/`. They are the single source: to change what a project gets, change them and create the project again.

The installed agents, commands and skills link to each other inside the project. Where they point at something that stays in this repo, such as a data file, the link goes to this repo on GitHub, pinned to the commit you installed from.

### Why the commands have a prefix

Some harnesses already use the plain names. Claude Code has its own `/review` and `/ship`, and Cursor has its own `/review`, so a project command with the same name would not run, or would hide the built-in one. The prefix keeps every loop command the same in every harness: `/sdlc-plan`, `/sdlc-design`, and so on. The loop commands column in the table shows the exact form.

## 4. Make it yours: AGENTS.md and PROCESS.md

Open the new project and edit `AGENTS.md` first. Every agent reads it on every task, so keep it short and only write lines that change what an agent does:

- **Stack**: the language, framework and main libraries.
- **Commands**: how to install, build, test, lint and run. Agents run these, so they must work from a clean checkout.
- **Conventions**: naming, layout, and the patterns to follow.
- **Boundaries**: what agents always do, what they ask about first, and what they never do.

Claude Code reads `CLAUDE.md`, not `AGENTS.md`, so the Claude Code layout adds a `CLAUDE.md` that imports `AGENTS.md`. Keep editing `AGENTS.md`.

Then read `PROCESS.md`. It is your profile's process: branches, reviews, gates and who signs off. Change it to match how you work. Fill in `ROLES.md` too, if your profile has one.

Commit before you start the loop, so the first run starts from a clean tree:

```bash
cd ../my-app
git add -A
git commit -m "Start from the AI SDLC Loop template"
```

## 5. Start the first loop

You talk to one agent, the coordinator. It plans the work, starts a producer and an adversarial reviewer for each phase in fresh contexts, lets each loop run until the reviewer passes the work, and comes back to you only at the end of the cycle. How you reach it depends on the harness: see **Start the coordinator** in your harness's section below.

The loop is a set of slash commands, run in order. Each takes a task, or the path to a brief:

- `/sdlc-plan`: turn the brief into a spec and a plan with checkable goals.
- `/sdlc-design`: design the modules, contracts and decisions the plan needs.
- `/sdlc-build`: implement the plan in small steps that keep the build green.
- `/sdlc-verify`: prove it works with tests and evidence, and find the root cause of what fails.
- `/sdlc-review`: review the change for security and quality.
- `/sdlc-ship`: get the reviewed change merged and released through your gates.
- `/sdlc-retro`: turn your feedback at the end of the cycle into proposed edits to the skills and checks.

You can give the coordinator the whole job in one command and let it decide which phases to run, or run the commands one at a time and read the output between them. [The commands](../docs/agents.html) on the site describe each one, and the installed project has the same reference in `.ai-sdlc/commands.md`.

Agents write their assumptions, open questions and blockers to a shared register, `.ai-sdlc/register.jsonl` by default, and the coordinator reads it as its inbox. Add `--register <path>` after a command's task to use another file. You can read the register at any time, and anything you add to it counts as an answer.

At the end of the cycle the coordinator writes `run-summary.md` with what ran, each reviewer's verdict, and the open questions with a recommended answer for each, then asks for your feedback. Give it, and it runs `/sdlc-retro` on its own. Proposed edits to skills go live only after they pass held-out tests and you approve them.

## 6. Your first request: a worked example

Say you want a small command-line tool that turns a CSV file into JSON.

1. Create the project: `scripts/new-project.sh --harness claude-code ../csv2json`
2. In `../csv2json/AGENTS.md`, set the stack (for example Python 3.12 and pytest), the test command (`pytest`), and a boundary such as "Never add a dependency without asking first". Commit.
3. Start your harness in `../csv2json` and reach the coordinator as your harness section says.
4. Type one request, with the outcome you want and how you will know it works:

```text
/sdlc-plan Build csv2json, a command-line tool that reads a CSV file and prints JSON to stdout.
Each row becomes an object keyed by the header row. A malformed row is reported on stderr with
its line number, and the tool exits non-zero. Done means: tests cover a normal file, an empty
file and a malformed row, and the README shows how to run it.
```

5. The coordinator sizes the job. It may ask you a few questions first, each with a recommended answer, such as what to do with an empty header. This is the only time it asks before the end of the cycle.
6. The plan producer writes a spec and a plan with numbered, testable goals, and the plan reviewer tries to fail it. Then carry on with `/sdlc-design`, `/sdlc-build`, `/sdlc-verify`, `/sdlc-review` and `/sdlc-ship`, each on the plan the last step wrote, or ask the coordinator to run them all.
7. Read `run-summary.md`, answer the open questions, and say what you would change. The coordinator runs the retro and proposes edits for you to approve.

Then ask for the next feature the same way. Keep each request to one outcome you can check. The smaller the request, the shorter each loop and the easier the review.

## Bootstrap for Cursor

For solo developers and people who do not code, using Cursor. Bootstrap asks two questions, sets up a new project, and opens it in Cursor. Then you tell the agent what you want to build.

### Why Bootstrap exists

The goal is to hand you over to a Cursor AI agent that understands what's going on and can handhold you from there into the decisions you need to make. You should never feel unassisted. As long as we follow that principle, Bootstrap doesn't need to do much: it gives Cursor a leg up in setting up a full SDLC that protects you, so you are not dependent on the AI model to do all the thinking, and you end up with beautifully engineered applications at a professional grade.

### Before you start

You need:

- Python 3
- Git
- cURL, if you download with the command below
- Cursor, signed in

Bootstrap does not install any of them. If Python 3 or Git is missing it stops and tells you in plain words. On Windows, run it in WSL.

### Get it and run it

Either download the repo with one command:

```bash
curl -fsSL https://github.com/mitulamin/ai-sdlc-loop/archive/refs/heads/main.tar.gz | tar -xz
cd ai-sdlc-loop-main
```

or clone it from its [Git URL](https://github.com/mitulamin/ai-sdlc-loop):

```bash
git clone https://github.com/mitulamin/ai-sdlc-loop
cd ai-sdlc-loop
```

Then, from inside that folder, run:

```bash
./scripts/bootstrap.sh
```

### What it asks, and what it does

It asks where you would like the project to be put, with the full path beside each choice: your home folder, your Documents folder (only if you have one), or the folder next to the one you are in. Then it asks what to call the project, which becomes the folder's name, and suggests one. If a folder of that name is already there and not empty, it says so and asks again. It never puts the project inside the ai-sdlc-loop folder.

Then it:

- copies the solo template and installs the coordinator, agents, skills and `/sdlc-*` commands into the project's `.cursor/` folder;
- adds an always-on Cursor rule and a `START-HERE.md` brief, with a short first-time note at the top of the rule and of `AGENTS.md`. They tell the agent what was set up and to work through the project's coordinator for every step of the SDLC. It talks in plain language, asks what you want to build one question at a time, fills in `AGENTS.md`, shows you the plan before it writes any code, and makes a commit for each step you approve;
- runs a local `git init` on `main` and leaves the first commit to the agent, which shows you what will be committed first. It creates no GitHub repository, no accounts and no remote, and nothing is sent anywhere;
- opens Cursor if its `cursor` command is available, and otherwise tells you to open the folder yourself.

Everything is written inside the new project. Bootstrap sets no Cursor or editor settings, model choices or workspace files, and changes nothing in your own Cursor setup. The rule stays on, and once `AGENTS.md` is filled in the agent skips the interview and starts from what you ask for.

To skip the questions, for example in a script, set `AI_SDLC_BOOTSTRAP_LOCATION` to `home`, `documents`, `parent` or the full path of an existing folder, and `AI_SDLC_BOOTSTRAP_NAME` to the folder name.

Teams and larger organisations should use `new-project.sh` and the steps above, which give you a choice of profile and harness.

## Harness by harness

Each section says what to install first, how the rules file is read, how to reach the coordinator, and where the harness works differently from the others. Each also links the official docs the layout follows.

<!-- BEGIN harness-details: generated by scripts/build-site.py from data/harnesses.json; do not edit -->
### Cursor

Cursor editor, CLI and Cloud Agents. Install Cursor and sign in. Create a project with `--harness cursor`.

**Rules file.** Cursor reads `AGENTS.md` at the project root as an always-on rules file. No other files are written.

**Start the coordinator.** Open Agent chat in the project and type a loop command, such as `/sdlc-plan`. The command tells the main agent to act as the coordinator, which starts the producers and reviewers as subagents.

**Where it differs from the other harnesses:**

- Cursor now treats slash commands as skills: the loop commands are skills with `disable-model-invocation` set, so they run only when the human types them. Legacy `.cursor/commands/` files still load, but the docs point new commands to skills.
- Cursor has no setting that makes a custom agent the main agent, so each loop command tells the main agent to act as the coordinator. Cursor lets the main agent and its direct subagents start subagents, which is the depth the loop needs.
- Cursor subagents take `readonly` rather than a tools list, and the reviewers must write their findings file, so reviewer tool limits stay a prompt rule, as in this repo's `agents/`.

**Official docs:** [install](https://cursor.com/download), [rules](https://cursor.com/docs/context/rules), [skills and commands](https://cursor.com/docs/context/skills), [agents](https://cursor.com/docs/context/subagents).

### Claude Code

Anthropic's Claude Code CLI, IDE extensions and desktop app. Install Claude Code, sign in, and check it with `claude --version`. Create a project with `--harness claude-code`.

**Rules file.** Claude Code reads `CLAUDE.md`. The installed `CLAUDE.md` imports `AGENTS.md` with `@AGENTS.md`, so `AGENTS.md` stays the one rules file you edit. Also written: `CLAUDE.md`, `.claude/settings.json`.

**Start the coordinator.** Run `claude` in the project. The project settings make the coordinator the session's main agent, so type a loop command, such as `/sdlc-plan`, straight away.

**Where it differs from the other harnesses:**

- Claude Code has merged custom commands into skills, so the loop commands are skills with `disable-model-invocation` set. Legacy `.claude/commands/` files still work.
- Claude Code reserves `/ship` for a bundled skill and keeps `/review` as a bundled alias, so commands with those names would not run. That is why the loop commands carry a prefix.
- The coordinator is the main session agent through the `agent` key in the project's `.claude/settings.json`. Remove that key, or start `claude` with `--agent` and another name, to work without it.

**Official docs:** [install](https://code.claude.com/docs/en/setup), [rules](https://code.claude.com/docs/en/memory), [skills and commands](https://code.claude.com/docs/en/skills), [agents](https://code.claude.com/docs/en/sub-agents).

### OpenCode

The OpenCode terminal agent, desktop app and IDE extension. Install OpenCode and connect a model provider. Create a project with `--harness opencode`.

**Rules file.** OpenCode reads `AGENTS.md` from the project root. Also written: `.opencode/opencode.json`.

**Start the coordinator.** Run `opencode` in the project. The project config makes the coordinator the default agent, and each loop command, such as `/sdlc-plan`, selects it too.

**Where it differs from the other harnesses:**

- OpenCode agents carry permissions, not a tools list. A reviewer without Bash gets a rule that denies `shell`; the agent name comes from the file name.
- The loop commands keep the shared prefix so they read the same in every harness, although OpenCode lets a project command replace a built-in one.

**Official docs:** [install](https://opencode.ai/docs/), [rules](https://opencode.ai/docs/rules/), [skills](https://opencode.ai/docs/skills/), [agents](https://opencode.ai/docs/agents/), [commands](https://opencode.ai/docs/commands/), [config](https://opencode.ai/docs/config/).

### Pi

The pi coding agent (pi.dev). Install Pi, check it with `pi --version`, and run `/login` in Pi to choose a model provider. Create a project with `--harness pi`.

**Rules file.** Pi reads `AGENTS.md` from the working directory and its parents as a context file. No other files are written.

**Start the coordinator.** Run `pi` in the project and grant project trust, which Pi needs before it loads `.pi/`. Then type a loop command, such as `/sdlc-plan`. The command tells the session to act as the coordinator.

**Where it differs from the other harnesses:**

- Pi has no built-in subagents. The agents go to `.pi/agents/`, the project folder that Pi subagent extensions read. Install one into the project with `pi install -l`, or let the coordinator start each agent as a separate `pi --print --no-session` process with `--append-system-prompt` pointing at the agent file.
- Pi calls slash commands prompt templates. Each loop command is a template in `.pi/prompts/` that tells the session to act as the coordinator.
- Pi loads `.pi/` only after you grant project trust.

**Official docs:** [install](https://docs.pi.dev/latest/quickstart), [rules](https://docs.pi.dev/latest/configuration), [skills](https://docs.pi.dev/latest/skills), [agents](https://pi.dev/packages/@tintinweb/pi-subagents), [commands](https://docs.pi.dev/latest/prompt-templates), [CLI](https://docs.pi.dev/latest/cli).

### GitHub Copilot in VS Code

GitHub Copilot chat in Visual Studio Code, Copilot harness. Install VS Code and sign in to GitHub Copilot. Create a project with `--harness copilot-vscode`.

**Rules file.** The Copilot harness reads `AGENTS.md` (or `.github/copilot-instructions.md`) as the project instructions file. No other files are written.

**Start the coordinator.** Open the project in VS Code, choose the Copilot harness in Chat, pick `coordinator` from the Agent dropdown, and type a loop command, such as `/sdlc-plan`.

**Where it differs from the other harnesses:**

- Prompt files (`.github/prompts/*.prompt.md`) run only in the Local harness, which VS Code has deprecated, so the loop commands are skills with `disable-model-invocation` set, which the Copilot harness runs as slash commands.
- Producers and reviewers set `user-invocable` to false, so only the coordinator shows in the Agent dropdown; the coordinator starts them as subagents.
- Reviewer tools map to the Copilot aliases `read`, `search`, `edit` and `execute`. The `edit` tool is there so a reviewer can write its findings file; not editing the work stays a prompt rule.

**Official docs:** [install](https://code.visualstudio.com/docs/setup/copilot), [rules](https://code.visualstudio.com/docs/copilot/customization/custom-instructions), [skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills), [agents](https://code.visualstudio.com/docs/agents/reference/custom-agent-file-reference), [commands](https://code.visualstudio.com/docs/copilot/customization/prompt-files), [subagents](https://code.visualstudio.com/docs/agents/run/subagents).

## Staying inside the project

The script writes only inside the new project. A few things are still done by the harness or by you:

- Most harnesses ask you to trust a folder the first time you open it, and remember your answer in their own settings. That is the harness's record, not a file the script writes. Pi loads `.pi/` only after you trust the project.
- Pi has no subagents of its own. If you add a Pi subagent extension, install it into the project with `pi install -l`, so it lands in the project's `.pi/` and not your user settings.
- Claude Code makes the coordinator the main agent through the project's `.claude/settings.json`. Your own user settings still apply on top, as they do in any project.

## Licences of the installed files

The project you create is MIT, from `template/`, and your code stays yours.

The copies of skills, agents and commands the script installs are MIT, like `template/` and the rest of your project, except files adapted from share-alike sources, which keep CC BY-SA 4.0 and carry their notice and licence text. Your project root holds one licence, the MIT `LICENSE`, and no project-wide notice. The bootstrap installs the same files for Cursor, and its `START-HERE.md` and always-on rule come from `template/`, so they are MIT too.

- Every installed file starts with a comment that names the file it came from and states the licence of that file.
- Every skill keeps its `SOURCES.md`. It credits the open-source projects the skill draws on, with the copyright lines and licence links their MIT and Apache licences ask for, and says where material was modified.
- A skill adapted from a share-alike source gets a `NOTICE.md` and a copy of the licence text in its own folder, and only such a skill does. An agent that includes the text of such a skill is under the same licence, and its comment points to that notice.
- If nothing you install is adapted from a share-alike source, no notice or licence copy is written.

Which files are share-alike is worked out from each source's licence in the repo's data, so a new share-alike source is handled the same way. If you edit a share-alike file, your edits are CC BY-SA 4.0 too, and you can share them on the same terms. Your own code and docs are not affected, and with no harness no skill, agent or command is copied. The scripts in this repo are GPL-3.0 and are not copied into your project.

## Things that stay in this repo

The agents mention a few tools and files that live in this repo, not in your project:

- `scripts/register.py` sorts and curates the register. It is not copied. The agents can append register lines themselves, and you can run it from your clone of this repo with `--register` pointing at your project's register.
- `data/scorecard.json` is where the coordinator records how each skill did. A new project has no such file until the coordinator creates one. Let it, or say in `AGENTS.md` that this project keeps no scorecard.
- Links to principles go to the matching installed skill, and links to data files go to this repo on GitHub.

To pick up a newer version of the skills and agents, create a fresh project from an updated clone and compare, or copy the changed files across, keeping the notice.
