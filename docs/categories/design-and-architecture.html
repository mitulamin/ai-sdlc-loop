Stage 2: Design and architecture

Shape the code so it is easy to change and easy to test.

Once you know what to build, decide where the boundaries go. Good seams and small interfaces make the next three stages cheaper.

18 principles

  1. 2.1 Design deep modules: a lot of behaviour behind a small interface
  2. 2.2 Choose seams deliberately; the seam is where tests and adapters attach
  3. 2.3 Keep framework, persistence and vendor details out of business logic, behind adapters
  4. 2.4 Separate orchestration (business rules) from reusable service operations
  5. 2.5 Add a layer or abstraction only for a concrete benefit
  6. 2.6 Record significant decisions as ADRs
  7. 2.7 Design for failure: explicit timeouts, bounded retries with backoff, circuit breakers, bulkheads
  8. 2.8 Bound every queue, cache, pool and result set, and decide what happens when full
  9. 2.9 Define the contract first
  10. 2.10 Use one consistent error shape across endpoints
  11. 2.12 Prefer adding over changing; assume every observable behaviour is depended on (Hyrum's law)
  12. 2.13 Make retried writes safe with idempotency keys derived from intent
  13. 2.14 Simple by default, complexity opt-in; avoid boolean flag parameters
  14. 2.15 State failure modes, retryability, timeouts and versioning in the contract
  15. 2.16 Keep a glossary of the domain language; one term per concept, used in code and tests
  16. 2.17 Split the domain into bounded contexts and map how they relate
  17. 2.18 Derive aggregates from events and commands
  18. 2.19 Challenge terms with edge-case scenarios while designing
