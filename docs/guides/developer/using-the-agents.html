Using the agents and commands

How to run the loop in this repo: who you talk to, what each agent and command does, the rules the loop follows, and how to keep it cheap. The agent and command files in agents/ and commands/ are the source of truth; this guide explains them. The agents page lists every agent and command with the skills it loads.

Why the loop works this way

The loop uses a coordinator model. The human talks only to a top-level coordinator, which starts new agents with blank contexts and fills each one with exactly the context it needs. Skills are layered: a short description is always in view, and the full skill is loaded only when a phase needs it. That layering is what makes the model cheap and reliable.

The aim is loops that run on their own from start to finish, come back to the human for feedback at the end, learn what they did not do well, and get better with each software project. Every mid-loop question to the human is a blocker that slows the process down, so the human stays out of each step. The human's judgement goes into the end-of-cycle review instead, and that review feeds the Learn category.

Before you start

  • A coding-agent tool that can start subagents and run slash commands. The agent and command files are plain markdown with front matter. Load them the way your tool expects; this repo does not install them for you. Skill 8.10 says to use your tool's own isolation and features rather than work around them.
  • A project with a short always-on rules file. The template's AGENTS.md is a starting point: run scripts/new-project.sh to create a project from it (see the home page). Keep it to stack, commands, conventions and hard boundaries, as skill 8.2 says.
  • Somewhere for run files. Briefs, outputs, findings files and the end-of-cycle run-summary.md are written to files, not pasted into the chat (skill 8.8). Scores go in data/scorecard.json.
  • Principle IDs resolve through aliases. Retired IDs are aliases of the principle they were merged into: 4.4 is now 4.1, 4.5 is 5.3, 9.4 is 5.1, 5.6 is 5.10 and 2.11 is 6.3. The coordinator resolves an alias before it briefs anyone with it.

The agents

There is one coordinator, plus a producer and an adversarial reviewer for each phase. Each phase loads the skills whose phase in data/skill-principle-map.json is that phase, so a category can feed more than one phase.

The commands

You give a command to the coordinator, and only to the coordinator. It runs each phase's loop on its own and reports at the end of the cycle.

CommandPhases it runsWhat it is for
/planPlanTurn the brief into a spec and a plan with verifiable goals.
/designDesignDesign the modules, contracts and decisions the plan needs.
/buildBuildImplement the plan in small, safe steps that keep the build green.
/verifyVerify, then DebugProve the build works with tests and evidence, and find the root cause of what fails.
/reviewSecure, then Review & shipReview the change for security and quality before it ships.
/shipReview & shipGet the reviewed change merged and released through the gates.
/retroLearnTurn the human's end-of-cycle feedback into proposed skill and check edits.

Three details matter:

  • /verify runs Debug only when the Verify output shows failing behaviour (a failing test, a bug or an unexpected result), and only for those failures. Then it runs Verify again on the fix.
  • There is one Review & ship phase, so /review and /ship start the same Review & ship producer and reviewer, each on its own task. /review runs Secure first.
  • /retro runs only after the human has given end-of-cycle feedback. The Harness phase has no command: the coordinator runs it.
  • Every command takes an optional --register <path> after the task, for example /plan Add CSV import --register .ai-sdlc/csv-import.jsonl. It names the register for the run; without it the default is .ai-sdlc/register.jsonl.

What producers and reviewers load

Every SKILL.md has the same sections, and the two roles load different ones on purpose.

  • Producers load each skill's When to use, its Do and Don't lists together, and its Steps. Getting the dos and don'ts in one pass means the producer builds to them from the start, instead of finding out about a don't only when the reviewer fails it.
  • Reviewers load only each skill's adversarial reviewer checks and its Don't list. A reviewer must not open the skills' SKILL.md files, because those hold the producer's Do lists. Without the Do lists, the reviewer cannot drift into grading taste or style; it hunts for breaches of the don'ts and known failure modes, and tests each acceptance criterion in the brief.

This split is principle 9.2: enforce standards at review, not by loading them all into the implementer's context. The separate reviewer itself is principle 7.1.

The rules of the loop

  1. Fresh-context agents. Every producer and reviewer starts in a new, blank context (8.7). The coordinator writes each one a brief to a file with exactly what the job needs (8.1, 1.6).
  2. The reviewer sees the result, not the reasoning. It gets the brief's task and acceptance criteria and the producer's output, never the producer's transcript. The producer's report is a claim to test, not evidence.
  3. Findings go to files. The reviewer writes only its findings file (8.8). The default verdict is FAIL until evidence shows otherwise. Every finding has a severity from P0 to P3 (7.5), the skill ID and check it breaks, and evidence: a file and line, or a command and its output. A check the reviewer could not run counts as a FAIL, because not run is not passed (4.9).
  4. Fix and re-review. On a FAIL, the coordinator starts a new producer with the brief and the findings file, then a new reviewer.
  5. Three FAILs in a row stops the phase. The coordinator records the phase as failed with its findings and notes it as a question about the approach, rather than trying a fourth time (5.5).
  6. Reviewers are never overruled. The coordinator does not override a reviewer's FAIL.
  7. No mid-cycle questions to the human. Agents send questions to the coordinator, through the register, even where a skill says to ask the human. The coordinator answers from the repo or the brief, or picks the recommended answer and records it as an assumption. The one exception is the interview at the very start of a project or epic, before any loop starts (1.4).
  8. The end of the cycle is the only exchange with the human. The coordinator writes run-summary.md (what ran, each verdict and findings file, the curated assumptions and open questions from the register, open decisions), fills in data/scorecard.json, and asks for feedback.
  9. /retro proposes; the human approves. The coordinator runs /retro on the feedback and closes with one report that gives the proposed edits and their results on held-out cases (9.9). An edit goes live only when the human approves it (9.10), every accepted or rejected edit is logged (9.12), and the Harness producer applies the approved edits at the start of the next run.

Assumptions, open questions and the register

Agents cannot ask you anything mid-cycle, so they need somewhere to put what they assumed, what they could not settle and what stopped them. Two things carry that, and both are required.

The output field. Every agent has one required output field, assumptions_and_open_questions. Its output ends with a section headed ## Assumptions and open questions, and that section holds a register-request block. If there is nothing to declare, the block says None. An agent definition that lacks the field, the block or the instruction below fails scripts/build-agents.py --check and scripts/check-skills.py, and a producer output without the section is a P1 finding for its reviewer. The field and the block are defined in data/agent-contract.json, and scripts/build-agents.py generates them into every agent, so nothing is hand-edited. Skills carry no output contract of their own, except skill 1.1, which tells its readers to use the block.

The register-request block. One line per entry, with the type inside the brackets, between two delimiter lines:

=== REGISTER REQUESTS ===
[ASSUMPTION: Dates in the CSV are ISO 8601; no locale-specific formats.]
[QUESTION: Should the import accept semicolon-separated files? Recommend yes.]
[BLOCKER: No sample CSV in the repo, so malformed-row handling cannot be tested.]
=== END REGISTER REQUESTS ===

An assumption is something the agent decided and carried on with, a question is something it wants answered (with its recommended answer in the statement), and a blocker stops it finishing. The types come from register.types in the contract data, so adding one is a data change only: the block, the parser and the validation follow.

Two ways into the register, one format. An agent that can write the register runs scripts/register.py ingest on its own output file, which writes each statement out verbatim. An agent that cannot, such as a reviewer with no shell, emits the same block in its findings file and again as plain text in its final message. Every agent definition says: "Agents that cannot write to the register themselves must emit the register-request block in their transcript. Any coordinator invoking such an agent must take those register requests as-is and write them out verbatim." So the coordinator ingests such a block without summarising, merging, rewording or dropping a line.

The register. It is a JSON Lines file, one JSON object per line, append-only. A line either declares an entry (id, agent, phase, type, text, status, ts, and optionally impact, urgency, recommendation and via) or updates an earlier one (ref, a new status, and optionally note, answer, by, impact and urgency). Statuses are open, surfaced, answered, dismissed and duplicate, and an entry's current status is its latest update. A block line carries no impact or urgency, so the coordinator rates the entry with an update line. The full field list, the meaning of the values and an example are in agents/README.md; scripts/register.py writes, lists and checks the register, and its selftest (run by build-agents.py --check) checks that the block parser round-trips every type.

You choose where it lives with --register <path> on any command, and it defaults to .ai-sdlc/register.jsonl. Whether you commit it or ignore it is up to you.

What the coordinator does with it. The register is the coordinator's inbox, and it pulls it rather than waiting to be told: before each brief, after each producer and reviewer finishes, and before the end-of-cycle report. It rates, de-dupes and ranks open entries (blockers first, then impact, then urgency), settles what it can from the repo or the brief, and batches the rest for you with a recommended answer for each, in the end-of-cycle report. A blocker it cannot settle stops only the work that depends on it. It records what it surfaced and what you answered as update lines, and acts on the answers.

It is never a required relay. Nothing is deleted or rewritten, so every raw entry stays readable in the file. You can read it at any point during a run, and you can answer an entry by appending an update line yourself; the coordinator picks it up at its next pull.

The phase model and the Learn loop

Each phase repeats the same producer and reviewer pair. When the human dislikes the final result, the Learn loop turns that into a stricter check for the phase that let the problem through. As a flow:

  1. Phase producer. Gets the phase's dos and don'ts together, in one pass, and produces the output.
  2. Adversarial reviewer. Checks the output only against the don'ts and known failure modes. If a check fails, the work goes back to a new producer (step 1). If it passes, the loop moves to the next phase.
  3. Next phase. The phases repeat this pair, in order, until the final result is ready.
  4. Human acceptance review. At the end of the full cycle, the human judges the final result. This is not in-development code review. If the human likes it, it is accepted and the cycle ends.
  5. Learn 1: which phase, and how. If the human dislikes it and explains why, the Learn skills find which phase let the problem through, and how.
  6. Learn 2: which do or don't rules. They trace it to that phase's do and don't rules.
  7. Learn 3: harden that phase's checklist. They propose new checks for that phase's adversarial reviewer, and a fix to the producer's rules where a rule was missing or wrong.
  8. Next run is stricter. Once approved, the same failure is caught at its own phase instead of reaching the human.

If a mistake is mechanical, the fix is a lint, hook or CI check rather than another rule in a prompt (9.1).

A worked example: one cycle

An illustration of a cycle on a small command-line app, the kind of project Testing the skills uses. The details are made up; the steps are the ones the loop follows.

  1. Brief. You tell the coordinator: /plan Add CSV import to the ledger CLI. The coordinator sizes the task (1.8), picks the Plan skills that apply, and writes a brief to a file.
  2. Plan. The plan producer writes a spec and a plan with a check for each step. The plan reviewer returns Verdict: FAIL with a P1 finding: there is no acceptance criterion for malformed rows. A new producer adds one, a new reviewer passes it, and the coordinator records both files.
  3. Design and build. You run /design, then /build. Each phase runs its own producer and reviewer loop without asking you anything.
  4. Verify, then Debug. /verify writes and runs the tests. One test fails on a file with a header row, so the Debug loop runs for that failure only: reproduce, find the root cause, fix, keep the test as a guard. Then Verify runs again and passes.
  5. Review and ship. /review runs Secure, then Review & ship. /ship takes the reviewed change through the gates.
  6. End of cycle. The coordinator writes run-summary.md, fills in the scorecard and asks for your feedback. You try the app and reply: blank lines in the CSV are skipped without a warning.
  7. Retro. The coordinator runs /retro. The Learn skills ask what conditions allowed it (9.5), find that the Verify reviewer had no check for silent skips, and propose one small edit to one surface (9.8), tested on held-out cases. You approve it, it is logged, and the Harness producer applies it at the start of the next run.

Keeping token cost down

Every token an agent reads costs time and money, and a crowded context makes the agent worse at its job. The biggest warning: the sources include very large catalogues, such as sickn33/agentic-awesome-skills and affaan-m/ECC, each with millions of tokens of skill text. Never load either wholesale. Even installing many of their skills costs you, because every installed skill's description sits in context on every turn.

  1. Keep the always-on file tiny. An AGENTS.md or CLAUDE.md is paid for on every turn. Aim for 1,000 to 2,000 tokens with stack, commands, conventions and hard boundaries only (8.2).
  2. Put everything else in on-demand skills. Only a skill's name and description are always loaded, about 100 words each; the body loads when the skill is triggered (8.3). Anthropic's skill-creator suggests keeping a SKILL.md under 500 lines.
  3. Use layers. A few-line stub, a short rule set read when triggered, and the full reference read only when the short rules are not enough.
  4. Write descriptions carefully. The description decides when a skill fires. A vague one misfires and loads a big body for nothing (8.4).
  5. Install few skills and subagents. Descriptions add up: 300 skills at about 100 words each is roughly 40,000 tokens before any work. Pick the ones your stack needs.
  6. Push heavy work to subagents. Reviews, audits and fact-finding in a fresh context keep the main thread small (8.7).
  7. Watch shared references. Some small skills read large shared guides. Check what a skill reads, not just its own size.
  8. Cut output tokens too. Terse answers and trimmed tool output save tokens; keep code, paths and errors verbatim (8.9).
