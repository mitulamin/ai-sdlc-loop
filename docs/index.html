What this is and why it exists

At Shravi Limited we are building aidev, a software engineering team in a box. I wanted agents that do real software work end to end without me steering every step.

The ideas for that are scattered across dozens of public repos: skills, sub-agents, slash commands and rules files. Many say the same thing in different words. Some contradict each other. Some are risky to install. And if you load them all, their descriptions alone use up the context window before the agent does anything useful.

So I had a research bot read 41 public repos and boil them down to 103 numbered principles in 9 categories. Each one is traceable to the repos it came from.

The principles are not the point. The point is the loop that produced them and the loop that keeps improving them. This repo is a base, not a finished product. Fork it, swap in your own principles, and let your own projects change it.

Who it is for

An individual and a large company share the same principles. What changes is ceremony: gates, roles, review and ownership. So there is one shared template, and three profiles that switch that ceremony on or off.

  • Individuals

    Working alone, on your own projects.

    Template profile solo

    One person. No gates, no roles file, no pull request template.

  • Small teams

    A few people sharing one repo.

    Template profile small-team

    A few people. One reviewer per change, a short roles note.

  • Large organisations

    Many people, with owners, gates and audit needs.

    Template profile large-org

    Many people. Review gates, code ownership, a roles file.

If you are unsure, start with solo or small-team. It is easier to add ceremony later than to remove it.

How it works

  1. One coordinator

    I talk to one agent, the coordinator. It does not do the work. It plans, then starts new agents with blank contexts and gives each exactly the context its job needs.

    An agent that has not seen the whole conversation cannot be misled by it.

  2. Producer and adversarial reviewer

    Every phase is a pair. The producer gets the dos and don'ts for that phase. The reviewer checks only against the don'ts and known failure modes, and is there to find problems.

    Loops run on their own and come back at the end of a cycle.

  3. Human review feeds Learn

    After the last phase there is a human acceptance review. My feedback goes to the Learn category (principles 9.1 to 9.12), which asks which phase failed, which rule was at fault, and how to harden the checklist.

    A change goes live only if it helps on held-out cases and a human approves it.

Start a project from the template

Clone the repo and run scripts/new-project.sh with a profile. It copies the shared base from template/, applies the profile, and runs git init. It refuses a target folder that is not empty.

git clone https://github.com/mitulamin/ai-sdlc-loop
cd ai-sdlc-loop
scripts/new-project.sh ../my-new-project              # solo, the default
scripts/new-project.sh ../my-new-project small-team
scripts/new-project.sh ../my-new-project large-org

Then edit the new project's AGENTS.md, read its PROCESS.md, and start your first loop. More in the README.
